# netOS — архитектура

netOS превращает любой ПК или ВМ на Debian в полнофункциональный роутер, управляемый
через веб-панель. Один бинарник, декларативная конфигурация, применение изменений
без перезагрузок.

---

## 1. Принятые решения

| Вопрос | Решение |
|---|---|
| Бэкенд | Go, один статический бинарник `netosd` со встроенным фронтендом; публичная команда `netos` — ссылка на тот же multicall-бинарник |
| Модель конфигурации | Декларативная: SQLite (ревизии) → рендер конфигов → атомарный apply |
| Откат | Каждое применение = ревизия; авто-rollback по таймеру, если админ не подтвердил |
| Файрволл | `iptables` (обязательное требование), атомарный `iptables-restore` |
| Маршрутизация по клиентам | fwmark + `ip rule` + отдельная routing table на канал |
| Режим перехвата канала | Безопасный TUN-контур; прочие режимы схема пока не принимает |
| VPN | И клиент, и сервер; всё настраивается из веб-панели |
| DNS/DHCP | Подключаемые провайдеры, выбор за пользователем |
| IPv6 | Активно подавляется на всех уровнях (anti-leak) |
| Доставка | Готовые бинарники из GitHub Releases + `install.sh` |
| Процесс | Фазами, каждая фаза даёт работающую систему |

## 2. Общая схема

```
                        ┌──────────────────────────────────┐
   браузер  ─── HTTPS ──┤  netosd (единственный процесс)   │
                        │                                  │
                        │  ┌────────────────────────────┐  │
                        │  │ HTTPS JSON API + polling   │  │
                        │  │ встроенный SPA (embed.FS)  │  │
                        │  └─────────────┬──────────────┘  │
                        │                │                 │
                        │  ┌─────────────▼──────────────┐  │
                        │  │ Config Store (SQLite)      │  │
                        │  │ ревизии, пользователи,     │  │
                        │  │ сессии, аудит              │  │
                        │  └─────────────┬──────────────┘  │
                        │                │                 │
                        │  ┌─────────────▼──────────────┐  │
                        │  │ Apply Engine               │  │
                        │  │ plan → validate → apply    │  │
                        │  │ → health-check → commit    │  │
                        │  │           или rollback     │  │
                        │  └─────────────┬──────────────┘  │
                        │                │                 │
                        │  ┌─────────────▼──────────────┐  │
                        │  │ Подсистемы (Subsystem)     │  │
                        │  └─────────────┬──────────────┘  │
                        └────────────────┼─────────────────┘
                                         │
      ┌──────────┬──────────┬────────────┼───────────┬──────────┬──────────┐
      ▼          ▼          ▼            ▼           ▼          ▼          ▼
   netlink   iptables   routing      dnsmasq/     hostapd   wireguard   xray /
   (адреса,  restore    tables +     unbound/                (kernel)   openconnect /
   бриджи,              ip rules     isc-dhcp/                          xl2tpd /
   VLAN)                             kea/dnsproxy                       strongswan
```

Все внешние демоны запускаются как отдельные systemd-юниты с конфигами,
которые netosd генерирует целиком. Ручная правка этих файлов бессмысленна —
они перезаписываются при следующем apply. Источник правды один: SQLite.

## 3. Модель конфигурации

Вся конфигурация — один JSON-документ, описанный Go-структурами. Он целиком
хранится в строке таблицы `revisions`. Это даёт бесплатно: атомарность,
историю, откат к любой точке, экспорт/импорт, diff между ревизиями.

```
Config
├── System        имя хоста, часовой пояс, NTP, параметры панели
├── IPv6Policy    режим подавления IPv6
├── Interfaces[]  физические, bridge, vlan, bond
├── Networks[]    L3-сегменты (LAN1, GUEST, DMZ...): подсеть, шлюз, VLAN, DHCP
├── WAN[]         аплинки: dhcp/static/pppoe/l2tp, метрика, health-check
├── MultiWAN      режим (failover / балансировка), веса, пробы
├── Firewall      зоны, политики, правила, port-forward, NAT, SNAT
├── DHCP          провайдер + общие опции + пулы + статические привязки
├── DNS           провайдер + upstream'ы (DoT/DoH/DoQ) + split-DNS + blocklists
├── Channels[]    каналы выхода: direct, wireguard, xray, openconnect
├── Policies[]    правила «кто через какой канал» (упорядоченный список)
├── VPNServers[]  входящие: wireguard, ikev2, ocserv, xray inbound
├── WiFi[]        hostapd: радио, SSID, привязка к сети
├── QoS           CAKE по WAN и лимиты клиентов
└── DDNS          Cloudflare, DuckDNS или No-IP
```

Учётные записи, сессии и аудит хранятся в отдельных таблицах SQLite, а история
счётчиков трафика — в защищённом runtime-файле с ограниченным сроком хранения.

### 3.1. Ревизии

```sql
CREATE TABLE revisions (
  id          INTEGER PRIMARY KEY,
  created_at  INTEGER NOT NULL,
  author      TEXT NOT NULL,
  comment     TEXT,
  config      TEXT NOT NULL,   -- JSON
  state       TEXT NOT NULL,   -- draft | applying | active | rolled_back | superseded
  applied_at  INTEGER
);
```

Ровно одна ревизия в состоянии `active`. Она же восстанавливается при загрузке
системы (netosd применяет активную ревизию на старте, до того как поднимет сеть).

## 4. Apply Engine

```
POST /api/config          сохранить черновик        → draft
POST /api/config/apply    применить                 → applying
POST /api/config/confirm  подтвердить (админ жив)   → active
       ↑ не пришло за N сек → автоматический откат  → rolled_back
```

Пайплайн одного применения:

1. **Validate** — проверка на уровне модели: пересечения подсетей, дубли VLAN ID,
   ссылки на несуществующие каналы, занятые порты, конфликты пулов DHCP.
2. **Plan** — каждая подсистема сравнивает старый и новый конфиг и возвращает
   список действий. План показывается в UI до применения («что именно изменится»).
3. **Apply** — подсистемы выполняются в фиксированном порядке (см. ниже).
   Каждая идемпотентна: повторный apply того же конфига не меняет состояние.
4. **Health-check** — проверка, что не отвалились: WAN-линк, DNS-резолв,
   доступность самой панели.
5. **Commit / Rollback** — если админ подключён по сети и правило файрволла
   отрезало ему доступ, он просто не сможет подтвердить, и система сама вернётся
   к предыдущей ревизии через `commit_timeout` (по умолчанию 30 секунд).

DNS blocklists загружаются только с HTTPS, ограничиваются по размеру,
нормализуются из plain/hosts/Adblock в отсортированный набор доменов и кэшируются
по URL. Перед preflight выбранного резолвера создаётся его отдельный managed-файл;
ошибка проверки, перезапуска или дальнейшего DNS Apply возвращает прежние байты
provider-файла и кэша. Если источник временно недоступен, используется только
ранее успешно разобранный кэш того же URL; отсутствие рабочего кэша прекращает Apply.

Порядок применения подсистем:

```
components → system → sysctl → ipv6 → netconf → interfaces → networks
      → wan → routing → channels → vpn-servers → policy → firewall
      → dhcp → dns → wifi
```

Порядок важен и в двух местах критичен. Правила файрволла и политики ссылаются
на интерфейсы, которых до шага `channels` может не существовать. А `netconf`
идёт перед подсистемами, назначающими адреса: в режиме прямого управления он
отбирает интерфейсы у systemd-networkd, и тот снимает выданные им адреса —
разрыв закрывают `interfaces`, `networks` и `wan`, идущие сразу следом.

Источник правды по порядку — `apply.Order` в коде; этот список повторяет его.

### 4.1. Интерфейс подсистемы

```go
type Subsystem interface {
    Name() string
    Plan(old, new *config.Config) ([]Action, error)
    Apply(ctx context.Context, cfg *config.Config) error
    Health(ctx context.Context, cfg *config.Config) error
}
```

## 5. Движок маршрутизации по клиентам

Это ядро системы. Требование: любой клиент может ходить через любой канал —
напрямую, через xray №1, через xray №2, через WireGuard, — и это же должно
работать для клиентов, которые сами пришли на роутер по VPN.

### 5.1. Каналы

Каждый канал получает три числа, выделяемые при создании и стабильные далее:

| Сущность | Значение |
|---|---|
| `channel.id` | 1, 2, 3, ... |
| routing table | `1000 + id` (имя `netos-ch<id>` в `/etc/iproute2/rt_tables.d/netos.conf`) |
| fwmark | `0x1000 + id` |

В каждой таблице — свой default route:

```
ip route add default dev wg0        table netos-ch1
ip route add default dev tun-xray1  table netos-ch2
ip route add default via <wan-gw>   table netos-ch3   # direct
```

И одно правило на канал:

```
ip rule add fwmark 0x1001 lookup netos-ch1 priority 20001
```

### 5.2. Маркировка трафика

`iptables -t mangle` в цепочке `netos-policy` (вызывается из PREROUTING),
правила генерируются из `Policies[]` в порядке приоритета:

```
-A netos-policy -m mark ! --mark 0x0 -j RETURN                 # уже промаркирован
-A netos-policy -s 192.168.1.50/32     -j MARK --set-mark 0x1002
-A netos-policy -m mac --mac-source AA:BB:CC:DD:EE:FF -j MARK --set-mark 0x1001
-A netos-policy -i wg-server0 -s 10.9.0.7/32 -j MARK --set-mark 0x1003
-A netos-policy -m set --match-set netos-dom-netflix dst -j MARK --set-mark 0x1002
-A netos-policy -j MARK --set-mark 0x1001                       # канал по умолчанию
-A netos-policy -j CONNMARK --save-mark
```

Плюс восстановление метки для ответных пакетов существующих соединений
в PREROUTING: `-j CONNMARK --restore-mark`.

Селекторы правила (комбинируются): исходный и конечный IP/подсеть, MAC,
сеть/VLAN, VPN-сервер и конкретный peer, порт назначения и протокол.
Доменные селекторы для обычных каналов используют IPv4 `hash:ip` на политику
с timeout 300 секунд. dnsmasq, принимающий клиентские запросы,
добавляет адреса DNS-ответов в эти наборы и ограничивает выдаваемый и кэшируемый
TTL теми же 300 секундами. При выбранном unbound или dnsproxy они работают только
как loopback-backend на порту 5355, а dnsmasq остаётся публичным frontend, поэтому
обучение наборов одинаково для всех трёх провайдеров. Подготовка новых наборов
идёт до firewall, удаление старых — после переключения правил; ownership-файл и
снимки `ipset save` обеспечивают точный rollback. Поскольку текущая маршрутизация
каналов построена на IPv4 iptables, валидатор требует фильтрацию AAAA и не обещает
несуществующую IPv6-маршрутизацию. Для входящего Xray применяется его собственный
matcher `domain:`, без kernel ipset.

### 5.3. Перехват userspace-каналов

Xray и OpenConnect работают через отдельный TUN-интерфейс. Дальше канал ничем
не отличается от WireGuard: default route находится в своей таблице, а путь
проверяется обычными `ip rule` и `ip route get`. TPROXY и SOCKS-only оставлены
за пределами текущей реализации, чтобы kill-switch и UDP не имели отдельного,
менее проверенного пути.

### 5.4. Утечки

Для каждого канала настраивается kill-switch: если интерфейс канала упал,
трафик привязанных к нему клиентов не должен уйти напрямую. Реализуется правилом
в конце таблицы канала:

```
ip route add blackhole default table netos-ch2 metric 1000
```

Плюс отдельное правило DROP в `netos-forward` для клиентов канала с
`fail_mode = block`. Альтернатива, выбираемая в UI, — `fail_mode = fallback`
с указанием запасного канала.

## 6. Подавление IPv6

IPv6 полностью подавляется — не «не поддерживается», а активно закрывается,
чтобы трафик не утёк мимо канала:

- `net.ipv6.conf.all.disable_ipv6 = 1`, то же для `default` и каждого интерфейса;
- `accept_ra = 0`, `autoconf = 0`;
- политика `ip6tables` — DROP на INPUT/FORWARD/OUTPUT (на случай, если модуль
  ядра всё же загружен и интерфейс поднялся до применения sysctl);
- DHCP-провайдер не поднимает DHCPv6, DNS-провайдер не отдаёт AAAA-записи
  (фильтр AAAA включён по умолчанию, отключаемо в UI);
- hostapd и VPN-серверы не анонсируют IPv6-префиксы;
- новые интерфейсы (включая TUN, поднимаемые каналами) прогоняются через
  тот же sysctl сразу после создания.

Режим настраивается: `off` (полное подавление, по умолчанию) или `passthrough`
на случай, если пользователь захочет вернуть IPv6 позже.

## 7. Подключаемые провайдеры сервисов

Пользователь выбирает реализацию в UI; netosd умеет ставить недостающий пакет
через apt и генерировать конфиг под выбранный демон.

### DHCP-сервер

| Провайдер | Комментарий |
|---|---|
| `dnsmasq` | По умолчанию. Лёгкий, DHCP+DNS в одном, простая статика по MAC |
| `isc-dhcp-server` | Классика, богатые опции, знаком администраторам |
| `kea` | Преемник ISC DHCP, REST-управление, hooks |

### DNS-резолвер

| Провайдер | DoT | DoH | Комментарий |
|---|---|---|---|
| `dnsmasq` | нет | нет | Только форвардер; DoT/DoH — через связку с одним из нижних |
| `unbound` | да | нет | Полноценный рекурсор + DoT-форвардинг, DNSSEC |
| `dnsproxy` | да | да | DoT/DoH/DoQ, upstream-правила по доменам |

Допускаются связки: `dnsmasq` держит DHCP и локальные имена, а апстримом ему
служит локальный `unbound`/`dnsproxy` с DoT/DoH. UI показывает получившуюся
цепочку резолва явной схемой, чтобы не было сюрпризов.

Split-DNS: для каждого канала можно задать свой upstream, чтобы имена
резолвились «изнутри» соответствующего туннеля.

## 8. VPN

### 8.1. Исходящие каналы

| Тип | Реализация | Интерфейс |
|---|---|---|
| `direct` | штатный маршрут через WAN | — |
| `wireguard` | ядро, `wg-quick` не используется — конфиг через netlink/wg | `wg-chN` |
| `xray` | `xray-core`: VLESS/VMess/Trojan/Shadowsocks, Reality, XTLS, WS, gRPC, mKCP | `tun-chN` |
| `openconnect` | клиент `openconnect` (AnyConnect/Pulse/Fortinet) | `tun-chN` |

Для Xray конфиг генерируется из формы в UI; поддерживается импорт ссылок
`vless://`, `vmess://`, `trojan://`, `ss://` и ручной outbound JSON.

Каждый канал имеет health-check (ICMP/TCP/HTTP до заданной цели через сам канал),
авто-реконнект и статус в панели: онлайн/офлайн, задержка, счётчики трафика,
внешний IP, который видит интернет через этот канал.

### 8.2. Входящие (VPN-серверы)

| Тип | Реализация | Что даёт |
|---|---|---|
| WireGuard | ядро | Роад-варриор, QR-код конфига в панели |
| IKEv2/IPsec | strongSwan | Нативные клиенты iOS/macOS/Windows без софта |
| OpenConnect | `ocserv` | Маскировка под HTTPS там, где режут WG/IPsec |
| Xray inbound | `xray-core` | VLESS+Reality для мест с жёстким DPI |

Каждому peer'у входящего сервера в панели назначается канал выхода — ровно тем
же движком политик, что и LAN-клиентам. То есть подключившийся по WireGuard
телефон может ходить в интернет через xray-канал роутера.

## 9. Multi-WAN

- Несколько аплинков с приоритетами и весами.
- Пробы живости: ICMP/TCP/HTTP до нескольких целей, порог потерь и задержки.
- Режимы: `failover` (строгий приоритет) и `balance` (взвешенный, через
  `iptables -m statistic` для распределения новых соединений по меткам WAN).
- Прилипание соединений (`CONNMARK`), чтобы установленные сессии не прыгали
  между аплинками.
- При переключении WAN каналы VPN автоматически переподнимаются поверх нового
  аплинка, а маршруты до VPN-эндпоинтов пересобираются.

## 10. Безопасность панели

- Первый запуск: инсталлер генерирует логин `admin` и случайный пароль, печатает
  их и удаляет временный файл с открытым паролем после успешного входа.
- Пароли — Argon2id. Сессии — HttpOnly cookie + CSRF-токен.
- Самоподписанный TLS-сертификат генерируется при установке. Пользовательская
  PEM-пара поддерживается. Порт и TLS меняются отдельной applying-ревизией через
  transient systemd unit: после restart проверяется ready-marker с точным ID,
  а при нестарте возвращается предыдущая active-ревизия. В режиме ACME сначала
  поднимается HTTP-01 listener на TCP/80, сертификат получается до запуска панели,
  а ready-marker создаётся только после успешного HTTPS-запроса к `/api/ping`.
  Сертификаты выдаются динамически и контролируются на обновление и срок действия.
- `netosd` принимает HTTPS на настроенном порту, а фактический доступ с WAN/LAN
  задаётся видимым правилом «Веб-панель netOS» в файрволле.
- Все изменения конфигурации пишутся в журнал аудита: кто, когда, что, diff.
- Ограничение попыток входа, блокировка по IP при переборе.

## 11. Раскладка на диске

```
/usr/local/bin/netosd                 бинарник
/etc/netos/netos.yaml                 параметры самого демона (порт, пути, БД)
/etc/netos/tls/                       сертификат панели
/var/lib/netos/netos.db               SQLite: ревизии, пользователи, метрики
/var/lib/netos/generated/             сгенерированные конфиги демонов
      ├── dnsmasq.conf
      ├── unbound.conf
      ├── iptables.rules
      ├── hostapd-<n>.conf
      ├── xray-ch<n>.json
      └── wg-ch<n>.conf
/etc/systemd/system/netos*.service    юниты netosd и дочерних демонов
/var/log/netos/                       журналы
```

Сгенерированные конфиги живут в `/var/lib/netos/generated/`, а не в `/etc`
соответствующих пакетов — так штатные конфиги дистрибутива не затираются, и
удаление netOS возвращает систему в исходное состояние. Юниты демонов
переопределяются drop-in'ами, указывающими на сгенерированные файлы.

## 12. Установка

```bash
curl -fsSL https://raw.githubusercontent.com/NymVetamin/netOS/master/install.sh | sudo bash
```

Скрипт:

1. Проверяет: Debian 12/13, root, архитектура amd64/arm64, наличие systemd.
2. Ставит базовые зависимости через apt (`iptables`, `iproute2`, `ipset`,
   `dnsmasq`, `wireguard-tools`, `ca-certificates`).
3. Скачивает релизный тарбол с GitHub, сверяет sha256.
4. Раскладывает файлы, генерирует TLS-сертификат и пароль администратора.
5. Определяет интерфейсы: угадывает WAN (тот, где default route) и LAN,
   формирует стартовую рабочую конфигурацию — роутер работает сразу.
6. Поднимает `netosd.service`.
7. Печатает адрес панели, логин и пароль.

Опциональные компоненты (xray, strongswan, ocserv, hostapd, unbound, kea)
ставятся по требованию из панели, когда пользователь включает соответствующую
функцию, — чтобы базовая установка оставалась лёгкой.

## 13. Реализованные этапы
